## 第 1 章　总则

### 1.1 数据集背景

GEPR-LINAN 是面向南宋都城临安（今浙江杭州）地理信息的命名实体识别与关系抽取数据集。语料来源于《咸淳临安志》《乾道临安志》《淳祐临安志》《梦粱录》《武林旧事》《都城纪胜》等 **18 个文本条目（来自 15 部源文献）**，共标注 4,920 条句子、25,397 处实体、17,881 条关系，涵盖 24 类地理实体和 34 类地理关系。

### 1.2 标注目标

1. 识别文本中所有地理实体的边界与类型；
2. 抽取实体间的地理空间关系；
3. 保证标注一致性，使不同标注者对同一文本的标注结果高度吻合。

### 1.3 基本原则

- **最大跨度原则**：优先标注完整的地理名称，包含修饰性定语（方位词、朝代词等）；
- **显式原则**：只标注文本中有明确语言证据的实体与关系，不做隐式推断；
- **单层原则**：不标注嵌套实体，取覆盖范围最广的外层实体；
- **句内原则**：关系只在同一句子内的实体对之间标注，不跨句。

## 第 2 章　标注流程

### 2.1 半自动标注流水线

本数据集采用"GPT-5 候选生成 → 人工核验修正 → 多轮迭代 → IAA 评估"的流水线：

```
原始句子
   ↓
GPT-5 生成候选标注（ERE 联合抽取）
   ↓
标注者 A 核验、修正
   ↓
[争议案例] → 标注者 B 复核 → 仲裁
   ↓
多轮迭代（共 4 轮）
   ↓
抽样 ~5,000 句由两位标注者独立标注 → 计算 IAA
   ↓
最终数据集发布
```

### 2.2 标注工具

- **数据集构建阶段**：无专用标注平台。GPT-5 以 JSON 格式输出候选标注，标注者直接在 JSON 文件中人工校验、修正实体跨度、类型及关系元组。
- **IAA 实验阶段**：标注者在纯文本上独立完成标注，直接输出与数据集格式一致的 JSON 文件，随后由脚本计算严格跨度级 F1 进行比对（见第8章）。
- **格式转换**：Python 脚本（LLM JSON / PLM json / PLM jsonl 三格式互转）

### 2.3 标注阶段

| 阶段 | 内容 |
|------|------|
| 第 1 轮 | 预标注：参照 GPT-5 输出，人工审核实体边界与类型 |
| 第 2–3 轮 | 纠错：重点处理边界模糊和类型争议案例，补充指南规则 |
| 第 4 轮 | 交叉核验：两位标注者分别标注同一批约 5,000 句，计算严格 F1 |
| 后处理 | 统一修正系统性错误，完成最终数据集 |

## 第 3 章　实体标注规范

### 标注通则

1. **最大跨度**：标注完整地名，包含修饰词（如"南宋故宫"整体标注）；
2. **不标代词**：泛指词（"此处""该地"）不标注；
3. **不做嵌套**：取最外层实体，内层不单独标注；
4. **语境判断**：同一字符串在不同语境下可能属于不同类型。

## 第 4 章　关系标注规范

### 标注通则

1. **方向性**：所有关系有方向，head 为关系发出方，tail 为接收方；
2. **句内原则**：不跨句标注；
3. **多关系**：同一实体对可有多个不同类型的关系；
4. **显式原则**：以文本显式表述为准，不做推断。

### 方向说明约定

> 下文中"A→B"表示 head=A，tail=B。

---

### 拓扑与位置关系

| ID | 关系名 | 方向与含义 | 示例 |
|----|--------|-----------|------|
| R01 | **位于** | A→B：A整体位置在B（较大范围）内 | 灵隐寺**位于**北山之麓 |
| R02 | **包含** | A→B：A在地理上包含B（A是B的上位空间） | 西湖**包含**苏堤 |
| R03 | **隶属** | A→B：A在行政上隶属于B | 钱塘县**隶属**临安府 |
| R25 | **距离** | A→B：A与B之间有具体距离描述 | 灵隐寺距西湖十里 |
| R26 | **相邻** | A→B（对称）：A与B紧邻 | 望仙桥与清河坊**相邻** |

| R33 | **交汇** | A→B（对称）：A与B（水道/道路）汇合 | 中河与盐桥河**交汇** |
| R34 | **交界** | A→B（对称）：A与B（行政区）边界相交 | 钱塘县与仁和县**交界** |

## 第 5 章　复杂情况处理

### 5.1 实体边界争议

- "大内之东"中只标"大内"，"之东"是关系信息，不纳入实体范围；
- 修饰性朝代词（"南宋""皇宋"）一般不纳入实体名，但已固化的专名（如"南宋故宫"）除外；
- 数词+量词+地名（如"三茅山"）整体标注为一个实体。

### 5.2 同名异地

同一文本中出现多个同名地点时，依据语境分别标注为独立实体，在标注说明中备注。若文献明确指出两处同名，可标注"别名"关系。

### 5.3 嵌套实体

不标注嵌套实体。出现嵌套时（如"临安府太府寺"），标注最外层实体整体，不单独标注内层。若两个实体在语义上独立并列出现，则分别标注。

### 5.4 关系方向性

- "A 在 B 之东" → head=A，tail=B，type=方位关系（东）；
- "B 之东为 A" → 方向同上；
- 对称关系（相邻、交汇、交界、相对）：只需标注一个方向，不重复标注。

### 5.5 隐式关系

只标注有明确语言证据的关系。例："灵隐寺大殿"中大殿属于灵隐寺，但若无显式表述则不标注"包含"关系。

## 第 6 章　GPT-5 辅助标注提示词

### 6.1 提示词结构

GPT-5 标注提示词分为两层：

- **System Prompt**：角色定义 + 合法类型枚举（含定义）+ 格式约束 + few-shot 示例
- **User Prompt**：待标注原始句子

### 6.2 System Prompt（Few-shot ERE 版，第3轮迭代后最终使用版本）

> **迭代说明**：本提示词为经过3轮人工校验反馈后的最终版本。相比初始版本，主要修订包括：（1）在 `【经济活动设施】` 与 `【市民生活】` 的定义中补充了明确的区分说明，以减少酒楼、茶坊等场所的归类混淆；（2）在 `【城市内部区划】` 与 `【行政区划】` 的定义中补充了层级说明；（3）在 `【包含】` 关系定义中强化了与 `【方位关系（内）】` 的方向区分说明；（4）将 few-shot 示例从 1 条扩展至 2 条，涵盖更多关系类型组合。具体混淆类型的系统性偏差分析见第 7.3 节。

```
你是中文古籍地理与机构信息抽取引擎。
我要你对给定的古籍文本进行地理实体提取和关系抽取。

【合法实体类型及定义】
【官署】古代政府办公机构。
【行政区划】国家划分的管理区域，用于地方治理。
【寺院】佛教宗教活动场所，供僧侣修行与信众朝拜。
【祭祀场所】用于祭祀神灵或祖先的场所，含国家祭祀与民间祭祀。
【交通设施】提供交通与驿传服务的设施。
【学校】教育与考试机构及其内部建筑。
【宫殿】皇室居住与理政场所。
【园林】供游览休憩的景观区域与建筑群。
【道观】道教宗教活动场所，用于奉祀神祇与仪式。
【经济活动设施】进行经济活动与仓储交易的场所，以盈利生产、仓储、税务为主要功能（注意：以娱乐消费体验为主的酒楼、瓦舍、茶坊等归【市民生活】，不归本类）。
【府邸宅邸】官员或富人的私人住宅，体现地位与居住文化。
【山脉】自然地理中的山体与相关地貌单元。
【城市内部区划】城市内部的坊、厢、铺等功能分区（注意：县级及以上行政区划归【行政区划】，乡村聚落归【乡镇】，不归本类）。
【桥梁】跨越水域或障碍的建筑，连接交通要道。
【水系】自然或人工水体。
【军事设施】用于军事目的的设施与编制相关实体。
【古迹】历史遗留建筑或遗址。
【民居】普通百姓的居住场所。
【街道】城市道路网络与相关街区名，构成城市骨架。
【乡镇】基层行政区划或聚居点。
【暂殡处所】王室贵族的暂时安葬之所，多设于寺院内。
【水利设施】水资源管理与利用工程，保障灌溉与防洪。
【市民生活】市民娱乐消费场所，如瓦舍、勾栏、著名酒楼、浴室（注意：以盈利生产或仓储为主要功能的归【经济活动设施】，不归本类）。
【社会福利设施】提供社会救助与福利的场所，照顾弱势群体。

【合法关系类型及定义】
【位于】地理实体1的位置在地理实体2。
【包含】地理实体1包含地理实体2（大→小，即1是容纳空间，2在其中）。注意与【方位关系（内）】方向相反：【方位关系（内）】表示实体1（小）在实体2（大）内，方向为小→大。
【隶属】地理实体1隶属于地理实体2（小→大）。
【别名】地理实体1的别名是地理实体2。
【旧名】地理实体1的旧名是地理实体2。
【更名】地理实体1更名为地理实体2。
【改建】地理实体1由地理实体2改建而来。
【迁移】地理实体1迁移到地理实体2。
【旧址位于】地理实体1的旧址位于地理实体2。
【距离】地理实体1与地理实体2之间有明确距离描述。
【相邻】两个地理实体紧邻。
【交界】两个地理实体边界相交。
【通往】地理实体1通往地理实体2。
【起点】地理实体1的起点是地理实体2。
【终点】地理实体1的终点是地理实体2。
【交汇】地理实体1与地理实体2交汇。
【方位关系（东/南/西/北/东南/东北/西南/西北）】地理实体1在地理实体2对应方位。
【方位关系（内/外/上/下/前/后/左/右/侧/相对）】地理实体1在地理实体2对应方位。

【极重要的格式与约束——逐字逐句遵守】
1) 输入是一段古籍中的句子，是你要识别的原始文本。
2) 实体类型仅能使用以上枚举，其余一律不要生成。
3) 关系类型仅能使用以上枚举，其余一律不要生成。
4) 返回结果为一个 JSON 对象，包含 ner 和 relations 两个字段。
5) ner 为二层列表：ner = [["实体名", "实体类型"], ...]
6) relations 为扁平五元组列表：
   relations = [["实体1名", "实体1类型", "实体2名", "实体2类型", "关系类型"], ...]
7) relations 中的实体必须在 ner 中出现，且类型一致。
8) 每条输入只输出一个 JSON 对象，键仅含 ner、relations；不要注释、Markdown、解释文字。
9) 若文本无实体：{"ner": [], "relations": []}
10) 有实体但无关系：relations 输出空列表 []
11) 实体的代词或缩写也要提取。

【示例（仅供参考，禁止复制到输出）】

示例1
输入："大内在凤皇山之东，以临安府旧治子城增筑。"
输出：{"ner": [["大内","宫殿"],["凤皇山","山脉"],["临安府","行政区划"]],
       "relations": [["大内","宫殿","凤皇山","山脉","方位关系（东）"],
                     ["大内","宫殿","临安府","行政区划","位于"]]}

示例2
输入："南曰丽正门，门外建东西阙亭、百官待漏院。"
输出：{"ner": [["丽正门","宫殿"],["东西阙亭","官署"],["百官待漏院","官署"]],
       "relations": [["丽正门","宫殿","东西阙亭","官署","方位关系（南）"],
                     ["丽正门","宫殿","百官待漏院","官署","方位关系（南）"]]}
```

### 6.3 User Prompt 格式

```
请严格按 JSON 结构返回：
{"ner":[[实体1名称,实体1类型],...],
 "relations":[[实体1名称,实体1类型,实体2名称,实体2类型,关系],...]}
原文 text：["待标注原始句子"]
```

### 6.4 两阶段分拆方案（RE-only）

当 NER 已由人工确认后，可单独调用关系抽取：

**System Prompt 核心差异**：

```
你是信息抽取引擎。NER 已完成，现给定实体列表，
请根据原文判定实体对之间的关系。
关系类型仅能使用枚举列表，其余一律禁止。
输出格式：[["主语实体","主语类型","宾语实体","宾语类型","关系类型"],...]
若所有实体对无关系，输出空列表 []。
关系中实体类型须与输入 ner 的类型一致。
```

**User Prompt 格式**：

```
原文 text："句子"
实体 ner：[["实体1","类型1"],["实体2","类型2"],...]
```

## 第 7 章　质量控制与标注者间一致性

### 7.1 IAA 计算方法

采用**严格 F1** 指标：

- **实体匹配**：文本跨度完全一致 **且** 类型一致
- **关系匹配**：head 实体、tail 实体、关系类型三者全部一致

**最终 IAA**（基于约 5,000 句抽样）：

| 任务 | F1 |
|------|----|
| 实体识别（NER） | **86.38%** |
| 关系抽取（RE） | **77.82%** |

### 7.2 争议仲裁流程

1. 核对指南，若有明确规定则依指南修改；
2. 若指南无明确规定，由第三位标注者或项目负责人仲裁；
3. 仲裁结果作为正例，并在指南中补充相应规则。

### 7.3 已发现并纠正的系统性偏差

| 偏差类型 | 描述 |
|---------|------|
| E08 vs. E20 | "经济活动设施"与"市民生活"混淆（如酒楼归类问题） |
| E05 vs. E11 | "城市内部区划"与"行政区划"边界不清（如"坊"的层级） |
| R02 vs. R20 | "包含"（A→B，A大）与"方位关系（内）"（A→B，A小）方向混淆 |

### 7.4 发布标准

| 指标 | 阈值 |
|------|------|
| 实体 IAA F1 | ≥ 80% |
| 关系 IAA F1 | ≥ 75% |
| 抽检错误率 | ≤ 5%（每轮抽查 5% 样本） |

## 第 8 章　标注者间一致性（IAA）实验专项规范

本章专门说明第 4 轮 IAA 实验的操作规范。该实验与建集阶段的标注任务在程序上**有本质区别**——标注者须从零独立标注，不得查看任何 GPT-5 生成候选，目的是评估指南本身的可操作性和标注者的一致程度。

---

### 8.1 实验设置与基本要求

| 项目 | 规定 |
|------|------|
| 参与人员 | 标注者 A 与标注者 B（即正式建集阶段的两位标注者） |
| 抽样方式 | 分层抽样：覆盖全部 **18 个文本条目（来自 15 部源文献）**及实体类型的全部 6 个功能大类 |
| 抽样数量 | 约 5,000 句（精确数以实际抽取为准） |
| 是否使用 GPT-5 候选 | **否**——两位标注者均不得查看任何预生成标注 |
| 是否互相可见 | **否**——两位标注者在各自完成标注前不得查阅对方结果 |
| 使用版本 | 两位标注者均使用**本指南最终版（v1.0）** |
| 标注工具 | 无专用标注平台；标注者直接输出与数据集格式一致的 JSON 文件 |

---

### 8.2 标注者的具体操作指令

1. **仅依据本指南标注**：标注过程中不得参考往轮标注记录，仅凭本指南规则和个人对文本的理解进行判断。
2. **独立完成，不讨论**：在提交各自结果前，两位标注者不得就具体句子进行讨论或对齐。
3. **对不确定案例的处理**：
   - 若对实体边界存在疑问，依照**第3章"最大跨度原则"**取覆盖范围最广的边界；
   - 若对实体类型存在疑问，依照各实体类型的**"排除"**条款逐步排除，选取最符合的类型；
   - 若对关系类型或方向存在疑问，依照**第4章关系通则**及**第5章复杂情况处理**操作；
   - 若以上仍无法判断，按个人最优判断直接标注，**不得留白不标**。
4. **不主动查阅建集结果**：实验期间不得参考数据集中已有的标注输出。
5. **完整标注所有句子**：不得跳过或以"句子过难"为由留空。

---

### 8.3 本实验适用的边界规则摘要

以下为 IAA 实验中最易出现分歧的点，标注者须在标注前重点复习：

| 规则编号 | 涉及内容 | 关键判断点 |
|---------|---------|-----------|
| E11 vs. E07 | 行政区划 vs. 官署 | 以**上下文功能**判断：指区域范围用 E11，指办公场所建筑用 E07 |
| E04 vs. E17 vs. E10 | 寺院 / 道观 / 祭祀场所 | 以**宗教属性**区分：佛→E04，道→E17，非宗教性祭祀→E10 |
| E08 vs. E20 | 经济活动设施 vs. 市民生活 | 以**主要功能**区分：以盈利生产/仓储为主→E08，以娱乐消费体验为主→E20 |
| E01 vs. E09 | 园林 vs. 宫殿 | 含"宫""殿"字且具皇家居住理政功能→E09；游赏性质的苑囿→E01 |
| R02 vs. R20 | 包含 vs. 方位关系（内） | 包含：A（大）→B（小）；方位关系（内）：A（小）→B（大），方向相反 |
| R07–R24 | 方位关系 | head 为被定位实体（A），tail 为参照实体（B）；"A 在 B 之东"→head=A，tail=B |
| R04 vs. R05 vs. R29 | 别名 / 旧名 / 更名 | 别名：共时；旧名：A 曾名 B（B 是旧称）；更名：A 更名为 B（B 是新称） |

### 8.4 提交与仲裁流程

1. 两位标注者**各自独立完成**全部约 5,000 句标注，以 JSON 文件形式提交；
2. 项目负责人运行比对脚本，对两份 JSON 文件计算**严格 F1**（计算方法见 7.1）；
3. 对于两者不一致的案例，优先检查：
   - 是否属于 8.3 表中的高频分歧类型；
4. 仲裁规则同 7.2：依指南→第三方仲裁→补充规则。
